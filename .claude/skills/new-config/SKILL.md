# Making a new ADT4 config

Everything lives in `dcist_launch_system/` (`$ADT4_DLS_PKG`). **Never hand-edit
`config/` or `tmux/autogenerated/`** — they are generated, committed, and CI
(`scripts/check_configs.sh`) fails if they differ from what the generator produces.
Edit only `config_generation/` and then regenerate.

## Layout

```
config_generation/
  experiment_manifest.yaml        # launch_configs, configs, important_variants, experiments
  base_params/<node>.yaml         # FULL parameter set for every node (shared by all configs)
  experiment_overrides/<config>/  # <node>_<suffix>.yaml overlays for one config key
  launch_components/<name>.yaml   # tmux window primitives (+ nodes_to_monitor)
  base_launch/base_launch.yaml    # tmuxp skeleton every session starts from
  generate_configs.py
```

Generated outputs:
- `config/<config_key>/<node>.yaml` — base params composited with overlays. Nodes load
  them via `conf_name:=$config` in `launch/master.launch.yaml`.
- `tmux/autogenerated/<experiment>-<config>.yaml` — the sessions `run-adt4` lists.

## Step 1: Decide what kind of change it is

Ask the user only if it's genuinely unclear. Most requests are one or more of:

| Want | Edit |
|---|---|
| Different parameter values for some nodes | new/changed `configs:` entry + `experiment_overrides/<key>/` |
| A new set of windows/processes | new `launch_components/<name>.yaml` and/or a `launch_configs:` grouping |
| A new runnable session (launch config × param set) | new `experiments:` entry |
| A brand-new node's parameters | new `base_params/<node>.yaml` (+ `launch_<node>` arg in `master.launch.yaml`) |

Read `experiment_manifest.yaml` first and reuse existing groupings rather than
duplicating them.

## Step 2a: Parameter overrides (`configs`)

1. Add the key under `configs:` in the manifest.
   - `my_config: []` → a leaf; its overrides live in `experiment_overrides/my_config/`.
   - `my_config: [relocalize, indoor]` → applies all descendant leaf overlays, in that
     order, **plus** `experiment_overrides/my_config/` if that directory exists (applied last).
   - Avoid including the same leaf twice transitively (the generator warns).
2. Create `experiment_overrides/my_config/<node>_overlay.yaml` containing **only** the
   changed keys. Copy the surrounding structure from `base_params/<node>.yaml`.
   - The base file is found by dropping the last `_`-separated token of the overlay
     filename: `hydra_overlay.yaml` → `hydra.yaml`. If the result doesn't match a file in
     `base_params/`, the overlay is **silently ignored** — double-check the name.
   - ROS-param files keep the `/**: ros__parameters:` wrapper (see
     `base_params/spot_executor_node.yaml`); config_utilities files (hydra, roman, ...) don't.
   - Maps merge recursively. Lists are **appended** by default; use `!replace [...]` to
     replace a list, or `!update` to merge element-wise (see
     `experiment_overrides/relocalize_awcd/hydra_multi_overlay.yaml`).
   - Keep substitutions in the style of the base file: `$(env X)` / `$(var robot_name)` for
     ROS launch params, `$<env X>` / `$<var robot_name>` for config_utilities files.
   - Non-YAML files in the override dir are copied verbatim into `config/<key>/`
     (filenames must be unique across all included leaves).
3. A config only gets rendered (composited) if some experiment uses it in its `config:` list.

## Step 2b: Launch windows (`launch_components` / `launch_configs`)

- New window primitive: `launch_components/<name>.yaml`, modeled on `roman.yaml`/`rviz.yaml`:
  ```yaml
  ---
  nodes_to_monitor:
    my_node: {}
  windows:
    - window_name: my_window
      shell_command_before: source ${ADT4_WS}/install/setup.zsh
      layout: tiled
      panes:
        - ros2 launch dcist_launch_system master.launch.yaml conf_name:=$config sim_time:=$sim_time robot_name:=$ADT4_ROBOT_NAME launch_my_node:=true
  ```
  `$config` and `$sim_time` come from the session environment. `nodes_to_monitor` entries
  feed the status monitor (`ADT4_MONITOR_CONFIG`).
- Any name with no entry in `launch_configs:` must be a file in `launch_components/`.
- Groupings compose: `my_stack: [main, hydra, my_window]`. Nearly everything should
  include `main` (= `core` + `status`).

## Step 2c: Experiments

```yaml
experiments:
  my_experiment:
    launch_config: [map, spot_real, sensors]   # groupings and/or primitives
    config: [default, my_config]               # one session file per entry
```

- Every key other than `launch_config` is a Cartesian-product axis exported as an env var
  in the session. Output name = `<experiment>-<value>[-<value>...]`; `true`/`false`
  values render as `-<key>` / `-no_<key>`. The example yields
  `my_experiment-default.yaml` and `my_experiment-my_config.yaml`.
- Put it in the matching section (base station / spot / phoenix / development).
- Add to `important_variants:` only if it should be listed first in `run-adt4`.

## Step 2d: New node / base params

Add `base_params/<node>.yaml` with the full default parameter set (it's copied into every
`config/<key>/`), and a `launch_<node>` arg + node block in `launch/master.launch.yaml`
that loads `$(find-pkg-share dcist_launch_system)/config/$(var conf_name)/<node>.yaml`.

## Step 3: Regenerate

```bash
source ${ADT4_WS}/install/setup.zsh   # puts composite-configs (config_utilities) on PATH
${ADT4_DLS_PKG}/scripts/generate_configs.sh
```

For debugging use the script directly with `-v`:
```bash
cd ${ADT4_DLS_PKG}/config_generation && ./generate_configs.py -v . ../config ../tmux/autogenerated
```

If `composite-configs` isn't found, the workspace isn't sourced/built — tell the user
rather than writing outputs by hand.

## Step 4: Verify

1. `git status` / `git diff` in `dcist_launch_system`: expect new/changed files only under
   `config/<key>/` and `tmux/autogenerated/`, plus your `config_generation/` edits.
   Unrelated diffs in generated files mean the tree was stale before you started — point
   that out instead of silently committing them.
2. Spot-check that the generated `config/<key>/<node>.yaml` actually contains the
   overridden values (catches misnamed overlays) and the session yaml has the windows
   you expect.
3. Watch generator output for `Requested key ... is not defined`, `specified N times`, and
   `Some important variants were not generated`.
4. New files under `config/` are installed by `setup.py` globs at build time, so a
   **new** config dir or file needs `colcon build --packages-select dcist_launch_system`
   (from `$ADT4_WS`) even with symlink-install. Edits to existing files don't.
5. Dry-run the session: `run-adt4 -d <experiment>-<config>`.
6. Pre-commit's `yamlfix` reformats `config_generation/` YAML (e.g. a one-item list becomes
   `[...]` flow style) and still reports "Passed". It skips the generated dirs, so after
   pre-commit runs, **regenerate again** and commit any changes. Otherwise CI's
   `check_configs.sh` fails.

## Step 5: Docs

If the session is user-facing, add a row to "Catalog of Supported Launch Configurations"
in the top-level `README.md`.
